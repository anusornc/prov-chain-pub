# ADR 0033: Use One Immutable Ciphertext and Per-Object DEK Envelopes

**Status:** Accepted
**Date:** 2026-08-30
**Context:** Durable protected-data sharing without per-recipient ciphertext copies or mutable key-distribution state
**Suite and codec fixed by:** [ADR 0034](./0034-pin-protected-data-suite-v1-and-canonical-privacy-encoding.md) — the complete mandatory `ProtectedDataSuiteV1`, canonical privacy encoding, and current recipient-key eligibility rule are fixed; implementation, Network Profile activation, and conformance evidence remain pending.
**Custody boundary fixed by:** [ADR 0035](./0035-keep-participant-private-keys-in-durable-client-only-custody.md) — participant clients alone retain the exact private wrapping-key versions needed to open immutable envelopes; services and the journal never hold or use them.
**Keystore suite fixed by:** [ADR 0036](./0036-pin-participant-keystore-suite-v1-and-whole-snapshot-commit.md) — exact private wrapping-key versions use one canonical encrypted snapshot and restore/reconciliation design; implementation, activation, and conformance evidence remain pending.

---

## Decision

Each **Protected Object** has exactly one immutable **Protected Payload Ciphertext** produced with one fresh random **Protected-Object Data-Encryption Key (DEK)**. That DEK is scoped to exactly one Protected Object and must not be reused for another object or later object version. The plaintext and unwrapped DEK never enter a Privacy Control Transition, Admitted Block Envelope, Ledger Journal, replicated state, RDF projection, API response, log, diagnostic, or plaintext backup.

The closed Participant Key Purpose for receiving an encrypted DEK is `privacy-key-wrapping`. It is distinct from `privacy-authorization`, node identity, PoA, governance, JWT, and wallet-at-rest keys. The owner must have an exact Active `privacy-key-wrapping` Participant Key Version at the verified parent before `CreateProtectedObject`; the grantee must have one before `GrantAccess`. This decision fixes that purpose and its envelope topology; ADR 0034 fixes its public-key algorithm, encoding, fingerprint, possession-proof scheme, and wrapping construction. The Network Profile must still reject activation until a conforming implementation and the required evidence exist and an exact profile version activates the complete suite and codec.

The canonical Protected Object Identifier is selected before encryption and is unique in parent Effective Privacy State. It must not be derived from ciphertext, an Owner DEK Envelope, or a final transition identifier that itself commits those bytes. This ordering lets the identifier enter cryptographic context without an identifier/ciphertext cycle. ADR 0034 fixes the concrete identifier encoding and generation requirements in the closed `ProtectedDataSuiteV1` schema.

`CreateProtectedObject` atomically commits exactly one:

- preselected canonical Protected Object Identifier;
- owner Participant Principal UUID and exact Active parent-state `privacy-authorization` authorizer-key reference;
- exact Active parent-state owner `privacy-key-wrapping` recipient-key reference;
- one versioned canonical Protected Payload Ciphertext record containing one suite identifier, one canonical nonce or equivalent public encryption input, one exact Payload Ciphertext-and-Tag Bytes field, and one profile-defined Protected Content Commitment;
- verifier-recomputable Encrypted Payload Commitment over the exact canonical Protected Payload Ciphertext record bytes;
- versioned **Owner DEK Envelope** addressing the same Protected-Object DEK to that exact owner wrapping-key version; and
- the normal network, profile, parent, expected-position, privacy-revision, transition-identifier, owner-signature, PoA, envelope, and receipt evidence required by ADRs 0016, 0017, 0028, and 0029.

There is no second ciphertext, recipient list, raw DEK, plaintext preview, external ciphertext or envelope locator, caller-selected owner alias, mutable metadata map, or ignored extension field. The complete Protected Payload Ciphertext record and Owner DEK Envelope bytes are journal data, not participant client-custody or Oxigraph state.

The Protected Content Commitment is constructed before `O`. ADR 0034 fixes its suite-defined construction, which may depend on the canonical protected content and Protected-Object DEK but must be independent of `O`, the payload nonce, Payload Ciphertext-and-Tag Bytes, Encrypted Payload Commitment, either DEK Envelope, transition identifier, and every signature or outer consensus field. This dependency rule prevents a content-commitment/AEAD cycle. ADR 0034 does not make plaintext authenticity publicly verifiable: keyless validators check only the commitment's canonical form, size, and binding into the signed object core.

The object constructor forms an acyclic, domain-separated public **Object Encryption Context Digest** before payload encryption. Its canonical pre-encryption core binds the protocol and schema versions; network identity; exact parent Network Profile identity and content hash; expected ledger position and privacy revision; parent Ledger Prefix Hash and parent envelope identity; preselected Object Identifier; owner principal; exact owner wrapping-key reference; Protected Payload Ciphertext and Owner DEK Envelope schema and suite identifiers; and the Protected Content Commitment. Let those profile-pinned, length-delimited bytes be `C_object_context`, and let:

```text
O = SHA-256("provchain/protected-object/encryption-context/v1" || C_object_context)
```

The payload AEAD associated data binds the raw 32 bytes of `O`. After payload encryption, the Encrypted Payload Commitment is computed over the exact canonical Protected Payload Ciphertext record bytes. The Owner DEK Envelope is one closed record containing `O`, one canonical public header with every required object, owner, recipient-key, suite, and commitment reference, and one opaque encapsulation/wrapped-key byte sequence. A conforming constructor uses suite-defined KDF/info and authenticated context to bind `O`, the Encrypted Payload Commitment, the owner principal, and the exact owner wrapping-key reference. The final `CreateProtectedObject` core and owner authorization signature then bind `O`, the Protected Content Commitment, the Encrypted Payload Commitment, and every exact ciphertext and envelope byte. ADR 0034 specifies the exact byte encoding and whether each field enters KDF info, AEAD associated data, or both; it does not omit or reinterpret any binding fixed here.

Let `C_create` be the profile-pinned canonical length-delimited bytes of the closed unsigned `CreateProtectedObject` core: the protocol, transition-schema, and variant identifiers; network and exact parent-profile identity and content hash; expected ledger position and privacy revision; parent Ledger Prefix Hash and parent envelope identity; preselected Object Identifier; owner principal; exact active owner authorization- and wrapping-key references; `O`; the complete Protected Payload Ciphertext record and Encrypted Payload Commitment; the complete Owner DEK Envelope; and authorizer kind exactly participant. It excludes the create transition identifier, Participant Authorization Signature, Proposal Digest, proposer signature, Envelope Hash, and Commit Receipts. Let:

```text
T_object_create = SHA-256("provchain/protected-object/create-transition-id/v1" || C_create)
A_object_create = SHA-256("provchain/protected-object/owner-authorization/v1" || T_object_create || C_create)
```

The raw 32 bytes of `T_object_create` are the unique `CreateProtectedObject` transition identifier, distinct from the preselected Object Identifier. The resolved owner `privacy-authorization` key signs the raw 32 bytes of `A_object_create`. The complete transition then adds `T_object_create` and that exact signature before the Scheduled Authority constructs the Proposal Digest and, later, the Envelope Hash. Neither `C_object_context` nor any encrypted field depends on `T_object_create` or the signature, so construction is acyclic while the final identifier and signature still commit every exact protected-data byte.

`GrantAccess` never encrypts the protected payload again and never creates another DEK. Its Grant Delivery Material `D` is exactly one versioned **Grant DEK Envelope** addressing the existing object's same DEK to the grantee's exact Active parent-state `privacy-key-wrapping` Participant Key Version; `D` has no sibling delivery fields. The Grant DEK Envelope is one closed record containing `Q`, one canonical public header with every required object, principal, recipient-key, suite, and commitment reference, and one opaque encapsulation/wrapped-key byte sequence. Multiple recipient envelopes, external recipient references, a group key, a client-custody locator, a raw shared secret, an Owner DEK Envelope replacement, or a caller-selected free-form `key_id` rejects.

ADR 0032 derives final Grant Identifier `G` from `C_grant`, which includes complete Grant Delivery Material `D`. Therefore `D` cannot cryptographically depend on final `G` without a cycle. Before constructing the Grant DEK Envelope, the owner constructs a **Delivery Context Digest** from canonical length-delimited `C_delivery_context` containing the `GrantAccess` protocol/schema identifiers; network and exact parent-profile identity; expected ledger position and privacy revision; parent prefix and envelope identity; Object Identifier; parent-derived owner; grantee; permission; referenced object's payload-suite identifier, Protected Content Commitment, and Encrypted Payload Commitment; exact grantee wrapping-key purpose, principal, version, algorithm, encoding, and fingerprint; and Grant DEK Envelope schema and suite identifiers. It excludes `D`, `G`, the owner authorization signature, Proposal Digest, proposer signature, Envelope Hash, and Commit Receipts. Let:

```text
Q = SHA-256("provchain/privacy-grant/delivery-context/v1" || C_delivery_context)
```

The Grant DEK Envelope records `Q`, and a conforming constructor uses the raw 32 bytes of `Q` in its suite-defined KDF/info and authenticated context. The complete `D`, including `Q`, public header, and opaque envelope bytes, then enters `C_grant`; ADR 0032's existing formula derives `G` over that completed core. Thus visible `Q` binds the signed envelope record to one proposed grant meaning and parent before encryption, while final `G` commits the exact resulting envelope without a signature or hash cycle. Recipient decapsulation and controlled vectors must reject transplantation across network, profile, parent, object, owner, grantee, permission, recipient key, suite, or content commitment. Keyless validators can verify the visible `Q` and outer commitments but cannot prove that an authorized constructor actually used `Q` inside opaque KDF/AEAD processing.

Creating a correct Protected Object or Grant DEK Envelope is a participant-side cryptographic construction obligation. The owner authorization signature authenticates the exact submitted bytes and owner intent; it is not a proof that the constructor used a fresh DEK, that owner and grant envelopes contain the same DEK, or that any private key can decrypt them.

**Public Envelope Validation** at Final Admission is deliberately keyless and deterministic. Under ADR 0034, every conforming, profile-activated healthy node verifies exact field cardinality; canonical identifiers and encodings; the single enabled suite; deterministic sizes and bounds; parent-state owner, grantee, key-purpose, version, status, algorithm, encoding, and fingerprint references; recomputed `O` and `Q` against their recorded fields; canonical Protected Content Commitment form and binding; the recomputed Encrypted Payload Commitment; transition identifiers; participant signatures; PoA evidence; and all outer envelope commitments. It rejects unknown suites or fields, empty/truncated/oversized material, wrong principals or key purposes, inactive creation/grant recipient keys, noncanonical bytes, publicly recomputable commitment or visible-context mismatch, stale parents, and transplantation of outer signed evidence without decrypting or consulting participant custody.

Final Admission cannot verify DEK randomness or cross-object non-reuse, authenticate the protected payload without the DEK, prove that two opaque envelopes contain the same DEK, prove that opaque wrapping bytes were constructed with the recorded `O` or `Q`, prove recipient decryptability from an envelope, or infer private-key possession merely from a wrapping public key. An authorized owner can therefore commit malformed or nondecryptable opaque material that passes public structural checks; the owner signature attributes those exact bytes but does not make them cryptographically correct. The separate `BindParticipantKey` possession proof required by ADR 0031 has the genuine public verifier fixed by ADR 0034; an owner signature, syntactically valid wrapping public key, or successful public encapsulation cannot substitute for it. Controlled owner/grantee decryption fixtures and published golden vectors provide functional evidence for fresh construction, same-DEK recovery, internal context authentication, transplant rejection, and plaintext round-trip; they do not become consensus-time claims.

The sole bounded-v1 protected-material fields in a Live Privacy Release are the exact committed Protected Payload Ciphertext plus exactly one applicable Owner DEK Envelope or Grant DEK Envelope for client-side recovery and decryption. They are not the whole response. Canonical release evidence also binds the network and profile, verified Network-Converged ledger position and Ledger Prefix Hash, Object Identifier, authenticated requester Participant Principal, selected recipient wrapping-key reference, and release-path kind. For the owner path, Final Admission-derived current object ownership and API authentication must both resolve to the same owner principal; the response binds that owner and uses the exact Owner DEK Envelope, with no self-grant. For a grantee, ADR 0032 additionally requires the exact grant to be Active at that release prefix, requires `authenticated requester principal == grant grantee == selected wrapping-key principal`, and binds its Grant Identifier and exact Grant DEK Envelope in the response. Both paths require ADR 0034's current recipient-key eligibility rule and the same stable read barrier. Neither path returns plaintext, an unwrapped DEK, a private key, a server-side decryption-oracle result, or an envelope from a historical audit view.

Object, grant, and participant-key lifecycles remain separate. Owner or grantee key rotation or revocation never rewrites the Protected Payload Ciphertext, Owner DEK Envelope, Grant DEK Envelope, or grant status. A later grant to another grantee adds only one new journaled Grant DEK Envelope. `RevokeGrant` changes only prospective managed authority and leaves every cryptographic byte unchanged. Regrant after terminal revocation uses ADR 0032's fresh Grant Identifier and a newly constructed Grant DEK Envelope; it never reuses or reactivates the old `D`.

Every exact ciphertext and DEK-envelope byte commits only at Ledger Journal append plus `fsync`. Failed object or grant construction before that point changes no authoritative state. After commit, projection failure degrades the node but cannot expose a half-object, an object without its Owner DEK Envelope, or an Active grant without its `D`. Verified Journal Replay and follower catch-up preserve and validate exact opaque bytes without regenerating randomness, encrypting, decrypting, unwrapping, consulting participant custody, or substituting a newer suite. An unknown committed historical suite yields an unsupported/degraded state rather than silent reinterpretation.

Same-parent object creation versus owner-key rotation/revocation, grant creation versus grantee-key rotation/revocation, duplicate Object Identifiers, and exact retries versus newly randomized replacement candidates serialize through the parent Ledger Prefix Hash, privacy revision, transition identifier, and exact envelope identity. Only one conflicting candidate can commit. Exact redelivery of an already committed envelope remains idempotent synchronization under ADR 0023; regenerated ciphertext or envelope bytes are a distinct candidate and never an exact retry.

This decision completes the structural protected-data topology but does not activate `PrivacyControlV1`. ADR 0034 now pins one complete mandatory `ProtectedDataSuiteV1`: payload AEAD and commitment construction, nonce/randomness rules, wrapping public-key type and encoding, real possession-proof verifier, KEM/KDF/wrap construction, exact envelope encodings and bounds, current recipient-key eligibility, cryptographic failure rules, libraries, and golden-vector requirements. Activation remains fail closed until a conforming implementation and the required evidence exist and an exact Network Profile activates that suite and codec. There is no per-object or per-grant algorithm negotiation in v1.

## Rationale

One per-object ciphertext separates the cost of protecting content from the number of recipients. Adding a grant appends only a small Grant DEK Envelope, while grant revocation preserves immutable history and does not pretend that already delivered cryptographic material can be recalled.

Per-recipient ciphertext copies would multiply storage, complicate equality and replay, and make granting look like object mutation. A long-lived group key would couple unrelated grants and make rotation or revocation ambiguous. External envelope locators would break the journal's self-contained recovery boundary. The selected topology keeps one durable payload and makes each owner-to-grantee authorization relationship explicit.

The two-stage `Q` then `G` construction preserves ADR 0032's Grant Identifier while giving the envelope an unambiguous grant-specific cryptographic context. Separating public validation from controlled decryption evidence avoids the false claim that walletless validators can prove facts hidden inside authenticated encryption.

## Consequences

- Effective Privacy State and replay need immutable object records containing one Protected Payload Ciphertext, its two distinct commitments, one Owner DEK Envelope, and grant records containing exactly one Grant DEK Envelope;
- object construction requires a participant-client-generated DEK and the owner's registered public wrapping key; grant construction additionally requires client-side owner recovery of that DEK and the grantee's registered public wrapping key, while follower admission remains walletless;
- protected-data relationships, object identifiers, owners, grantees, key references, suite identifiers, and opaque byte lengths remain visible to permissioned nodes even though plaintext and DEKs do not;
- the owner path must use the same Network-Converged Live Privacy Release barrier as the grantee path and cannot treat possession of the Owner DEK Envelope as current-tip authority;
- participant client custody must retain the exact Active and Retired private key versions required by ADRs 0034 and 0035 for immutable historical envelopes, without treating local retention as lifecycle authority;
- fixtures must cover exact object and grant canonical forms; preselected identifier and `Q`/`G` acyclicity; cross-network/profile/parent/object/owner/grantee/permission/key/suite transplantation; wrong cardinality; empty, truncated, oversized, or noncanonical fields; inactive or wrong-purpose wrapping keys; commitment mismatch; and rejected-candidate non-mutation;
- controlled cryptographic fixtures must show owner and grantee envelopes recovering the same object DEK, the single ciphertext decrypting to the expected plaintext, wrong keys and every changed context failing, fresh objects using independent DEKs, and no plaintext or unwrapped DEK entering evidence output;
- concurrency and crash fixtures must cover key binding before object creation, object before grant, same-parent create/key and grant/key races, duplicate identifiers, exact retry versus regenerated bytes, failures immediately before and after `fsync`, partial projection failure, restart, and no half-object or grant without `D`;
- three-node evidence must show byte-identical payload and envelope material, identical Effective Privacy State digests, walletless follower validation, exact restart recovery, additive grants without ciphertext change, and revocation without cryptographic-byte mutation; and
- cryptographic recall, automatic re-encryption, proxy re-encryption, hidden recipient metadata, server-side plaintext release, ownership transfer, object mutation, and per-recipient algorithm negotiation remain outside bounded v1.

## Implementation Status

Accepted structural architecture; ADR 0034 fixes the protected-data cryptographic suite and codec, ADR 0035 fixes the client-only custody boundary, and ADR 0036 fixes the exact at-rest keystore design, but implementation, Network Profile activation, and conformance evidence remain pending. `src/security/encryption.rs` is partial raw-key scaffolding: it encrypts plaintext with a caller-supplied shared 32-byte key using `XChaCha20Poly1305`, no associated data, a random 24-byte nonce, hex strings, and a free-form `key_id`. Although it can generate a random 32-byte key, legacy encrypted-transaction builders reuse one server-wallet-held `private_data_key` across protected records rather than create a per-object DEK. There is no ADR-defined per-object identity or content/payload commitment, Owner DEK Envelope, Grant DEK Envelope, recipient public key, KEM, wrapping proof, same-DEK construction, or conforming participant client custody.

`TransactionPayload` has only RDF and Governance variants, and `NetworkProfile` has no privacy-control schema, `ProtectedDataSuiteV1`, or fail-closed privacy activation gate. `src/wallet.rs` stores unversioned raw shared secrets by free-form key ID rather than purpose/version-aware wrapping keys and can serialize those secrets into plaintext JSON backups. The conditional encrypted-query path expects a transaction-ID map, attempts server-side decryption from a local wallet secret without an Active grant or converged release barrier, and returns recovered plaintext as `decrypted_data`; ordinary JWT subject construction and that UUID-based lookup are themselves inconsistent. The encrypted writer uses a different shape. Authoritative block/WAL reload reconstructs encrypted payloads as empty strings, while the RDF projection may incidentally retain a separate ciphertext copy, leaving inconsistent persisted copies and recovery paths.

Existing wallet-encryption tests manually reimplement a separate `ChaCha20Poly1305` 12-byte-nonce format rather than exercise `WalletManager` or protected-data envelopes. `tests/privacy_test.rs` is an in-memory raw-key correct-key/wrong-key test. There is no encrypted restart and hash-reproduction, one-ciphertext identity, owner/grantee same-DEK recovery, context-tamper, crash-atomicity, rejected-candidate, or three-node convergence fixture. Low-level encryption, random-key generation, and outer block hashing are useful scaffolding, but no current code or test demonstrates conformance to this decision. No implementation code changed with it.
